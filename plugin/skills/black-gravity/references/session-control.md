# Session messages and task control

Reference for the [core skill](../SKILL.md). Open it when using `black_gravity_send_message`, discard or cleanup, or on `SERVER_RESTARTED` or `ORPHAN_PROCESS_RUNNING`.

## Talking to the session

Use `black_gravity_send_message` with taskId, a stable UUID messageId and text of up to 2,000 characters. Keep the ID and the text: repeating the same values queries the existing receipt. On an ambiguous transport error, do not automatically generate another ID. `queued` waits for the current turn; `sent` reports acceptance of a continuation, without proving that the model read it. Failure or cancellation does not authorize automatic repetition and additional quota consumption.

Follow `continuationTaskId` with cursor zero. If `continuationPending` is active without an ID, keep waiting on the current turn; `ready` ends that turn, not the pending sequence. Resuming keeps the session, copy, selection, skills, role, mode, criteria and limits. Text does not approve integration or permissions.

## Continuation and control

- Use the `taskId` of a completed task—or of a failed/timed-out task whose checkpoint and process cleanup are proven—with `black_gravity_resume` to restore its exact checkpoint bytes into the canonical workspace; explicitly cancelled task IDs remain refused (`INVALID_SESSION`). Provide exactly one of `taskId` and `sessionId`, the latter obtained through `black_gravity_status`. If the prior turn recorded a conversation ID, the bridge continues via `--conversation`; if no conversation ID exists—or if the provider reliably reports that the recorded conversation is absent after verified clean process exit, zero tool steps, and unchanged workspace bytes—it starts a fresh conversation with a brief informal notice summarizing safe cause and work without embedding raw follow-up prompts or patches (preserving refusal on generic errors or unverified process exit). `black_gravity_sessions` lists persisted sessions and `black_gravity_tasks` recovers task IDs after a restart. Interrupted runs are not repeated automatically: examine `SERVER_RESTARTED` and the workspace before starting other work. If there is `ORPHAN_PROCESS_RUNNING`, wait for the registered process to end; do not try to apply or discard its copy.
- When the user asks for cancellation, call `black_gravity_cancel` with the `taskId` and confirm the status. Cancellation ends the local process; partial changes may remain.
- When the user wants to discard the work, call `black_gravity_discard` after the task ends. Neither manual discard nor automatic retention cleanup releases a root whose process cleanup is unconfirmed (including `tracked` launches), preserving markers, records, and bytes until valid reconciliation confirms termination. Once confirmed, discard removes that lineage's archived checkpoints and receipts, and removes the canonical workspace directory when no other retained task uses that root. Use `black_gravity_cleanup` to remove expired checkpoints/workspaces; the default retention is 7 days. `black_gravity_health.maintenanceIssues` with `copy-cleanup` indicates a failure of the automatic cleanup (the server keeps running and tries again every minute); examine the `code` before calling `black_gravity_cleanup`.
- After a failure or timeout, examine the events and the copy before repeating the task. Do not start a new run automatically if it could repeat effects or consume quota.
