# Configuration, isolation, and security

## Architecture

Black Gravity was previously named Antigravity MCP Bridge and distributed as `antigravity-mcp-bridge` through the published 0.9.0. See [available versions](setup.md#available-versions) for the current names.

```text
Codex -- MCP stdio --> bridge -- subprocess --> official agy --> Antigravity
Codex <-- structured events and results <-- bridge <-- stdout/stderr
```

Codex can start tasks, follow events, inspect results and cancel processes. The bridge inspects candidate project files locally during preflight. The official `agy` CLI handles service communication, and the bridge does not read private endpoints, cookies or CLI authentication stores.

## Git isolation and patch encoding

Local Git uses a dedicated environment with `PATH` restricted to directories outside the project and copy. Hooks, fsmonitor and global execution settings are disabled. Ignore rules are queried separately, preserving the authentication policy of `agy`. When Git termination cannot be confirmed after a termination request and bounded grace period (for example, when pipes remain open), the operation fails with `GIT_CLEANUP_UNVERIFIED`. The bridge destroys stdio and marks the private baseline to block reuse, preview, integration or unsafe deletion of potentially held resources.

Text patches containing non-UTF-8 bytes fail with `UNSUPPORTED_PATCH_ENCODING`. Mark files as `binary` in `.gitattributes` to keep original bytes in Git binary patches. Before starting a write task, the bridge also refuses files that are non-UTF-8 and would produce text diffs. This includes a set `diff` attribute or an unspecified one with no NUL byte in the first 8,000 bytes. An explicitly unset `diff` attribute, as with `binary`, prevents a text diff. The bridge reports those paths with `UNSUPPORTED_TEXT_ENCODING` before starting the CLI. Mark them as `binary`, leave them out of `includePaths` or convert them to UTF-8. Read-only tasks generate no patch and are exempt from this refusal.

## Host permissions

`black-gravity permissions` prints a permission block generated from the tool annotation table. It writes only to stdout. Review and merge the output into the host configuration.

1. Print the block from an installed or source build.

   ```powershell
   black-gravity permissions --host claude-code
   node .\dist\src\index.js permissions --host claude-code --preset delegation
   ```

2. Select a preset. The default `connector` allows tools with `readOnlyHint: true` and asks before all other tools. `delegation` allows the delegation flow and asks only for `DELEGATION_ASK_TOOLS` in the code: `black_gravity_integrate`, `black_gravity_discard`, `black_gravity_cleanup`, `black_gravity_memory_remove`, `black_gravity_set_sandbox_policy`, `black_gravity_cancel` and `black_gravity_group_cancel`. Match `--profile` to `BRIDGE_TOOL_PROFILE` (default `full`) so the output covers only registered tools. Match `--server-name` (default `black-gravity`) to the registered server key because rules use `mcp__<server>__<tool>`.
3. Add repeatable `--deny <tool>` options using a bare tool name or `mcp__<server>__<tool>`. An incorrect prefix, unknown tool or tool outside the profile produces an error and exit code 2 with no stdout output.
4. For Claude Code, merge the `allow`, `ask` and `deny` arrays into `permissions` in `~/.claude/settings.json`, `.claude/settings.json` or `.claude/settings.local.json`, keeping existing rules. Start a new session. To try the block first, save it to a separate file and start `claude --settings <file>`.
5. For Codex, use `--host codex`. The TOML prints one `[mcp_servers.<server>.tools.<tool>]` table per tool with `approval_mode = "approve"` or `approval_mode = "prompt"`, and lists denied tools in `disabled_tools` under `[mcp_servers.<server>]`. Merge into the existing server entry in `~/.codex/config.toml` and combine any existing `disabled_tools` lists in one key. The keys were checked against the Codex configuration schema. Per-tool `approval_mode` behavior in a Codex session remains unverified. Codex ignores unknown keys, so inspect the result with `codex mcp get <server> --json`.

Host approval and [bridge approval](review-and-integration.md#approval-and-integration-modes) both apply. A host rule allowing `black_gravity_integrate` leaves the bridge form active in `ask` mode. A host `ask` rule still applies in bridge `auto` mode. All bridge verification, test and review requirements apply in both modes.

## Bundled Anti-AI Craft

The package includes a verified six-skill [Anti-AI Craft snapshot](https://github.com/Zythenth/anti-ai-craft). Every new task gets `anti-ai-code` and `anti-ai-security` in the copy, and Gemini is instructed to read them before starting. `anti-ai-design`, `anti-ai-design-flow`, `anti-ai-audit` and `anti-ai-remediate` appear as a catalog of names, descriptions and paths (up to 8 KiB). Their bodies, references and images stay outside the prompt and are available on demand, read-only, in a private per-revision copy under `<state>/anti-ai-craft/` added with `--add-dir`. Under tool policy, hooks allow only reads there. Gemini selects relevant skills without requiring their literal names in the task.

Before each new task, the bridge verifies file size and SHA-256 against the snapshot manifest. Missing or altered content fails with `CRAFT_SNAPSHOT_INVALID` or `CRAFT_SNAPSHOT_MISSING`. Reinstall the bridge version to restore the snapshot. The bridge performs no automatic download. Resumes and handoffs retain the original snapshot. The permanent skills count toward the eight-package and 1 MiB limits. Identical same-name skills are deduplicated. Conflicting content fails with `SKILL_CONFLICT`. Skill files are excluded from the project patch.

`BRIDGE_ANTI_AI_CRAFT=off` is no longer supported; opt-out is rejected explicitly (`opt-out-unsupported` in `configurationIssues` and `optOutRejected` with migration guidance in `black_gravity_health.antiAiCraft`), and the permanent skills still load in every delegated session. Remove the variable. Sessions without the Anti-AI Craft snapshot are refused before execution with `CRAFT_REQUIRED`. Each task records `craftLoad` with the `delivered` permanent skill names and SHA-256 digests and `initListing` (`'listed'`, `'not-exposed'`, or `'not-observed'` when no init event was received for that session, plus bounded `listed` names when exposed); `agy` `init` currently does not list skills, so loading is evidenced only by delivery. `BRIDGE_ANTI_AI_CRAFT_DIRECTORY` selects a snapshot in the same format, verified against its manifest. The bundled manifest digest is pinned in the release build and checked before use, whereas an opt-in override directory is checked only against its own manifest. `black_gravity_health.antiAiCraft` reports source, revision, version, manifest digest and readiness without network access or state writes. Maintainers run `node scripts/update-anti-ai-craft.mjs --check` to confirm a clean fetch of the pinned revision reproduces the committed snapshot. The bundle provides skills without installing the Anti-AI Craft MCP, Graphify, Python or other tools mentioned by those skills. The visual library images retain their original licenses. See [dependency notices](../THIRD_PARTY_NOTICES.md).

## Client-provided skills

Codex or another client can send selected skills in `black_gravity_run.skills`. Compact delivery returns only the name, hash and file count in `providedSkillSummaries`. A package contains `SKILL.md` text and optional text resources whose paths are relative to the skill:

```json
{
  "workingDirectory": "/absolute/project/path",
  "prompt": "Use the review-style skill to review the project.",
  "mode": "read-only",
  "skills": [{
    "name": "review-style",
    "content": "---\nname: review-style\ndescription: Review rules\n---\nRead references/check.md before reviewing.",
    "resources": [{ "path": "references/check.md", "content": "Check the requirements against the actual files." }]
  }]
}
```

The bridge stages only the supplied packages under `.agents/skills/<lowercase-name>/` inside the copy. It preserves the declared name and UTF-8 bytes, including names such as `Presentations`. Metadata includes names, relative paths and hashes without repeating skill text. Clients select resources explicitly and keep private files and credentials out. Global skills are not discovered or imported automatically.

Limits are eight skills, 100 resources per skill and 1 MiB of text total. These files count toward copy limits. Absolute paths, traversal, device names, case aliases, links and collisions with existing directories are rejected. Staging does not run supplied scripts. Tool dependencies must be present in `agy`, and a skill grants no permissions.

Resumes and handoffs retain the original packages and hashes. Resumes reject a new `skills` argument, even an empty list. Adding, changing or removing a supplied resource invalidates verification. Auxiliary files stay out of project patches. Omit `skills` to keep using eligible skills already in the project.

## Repository agent configuration

Repository `.agents/` paths (at any depth, matched case-insensitively) are never copied into the isolated project copy, and `includePaths` entries containing a `.agents` segment are rejected with `INVALID_INCLUDE_PATH`. The copy only holds agent configuration generated by the bridge: staged execution policy files when an agent policy is active, the guard hook (`.agents/hooks.json` and `.agents/bridge-guard-hook.mjs`) when no agent policy is set, and bridge-provided skills under `.agents/skills/`.

When no agent policy is set, the guard hook covers the five native file write tools (`write_to_file`, `write_file`, `replace_file_content`, `multi_replace_file_content`, `edit_file`) with exact matchers: it denies all matched writes in `read-only` mode, and in `write` mode denies conflicting path-like keys, malformed or relative targets, targets outside the copy, any `.agents` or `.git` path segment relative to the copy root (case-insensitively), symlinked or non-directory ancestors, and symlinked, non-regular, or multi-link targets. Other `agy` tools without an agent policy are not covered by the guard hook; however, any unexpected, modified, symlinked, or case-variant agent configuration found in the copy causes the bridge to refuse the next CLI launch, resume, or repair before starting `agy` with `AGENT_CONFIG_IN_COPY`.

Preview and integration also refuse any patch touching `.agents`, `.git`, or OpenCode configuration (`opencode.json`, `opencode.jsonc`, and `.opencode/`, at any depth, matched case-insensitively) with `AGENT_CONFIG_IN_PATCH`, leaving the original repository untouched. Tasks therefore cannot edit the project's `.agents/` directory or OpenCode configuration. Instruction-only files (`GEMINI.md`, `AGENTS.md`) are still copied as ordinary project files.

## Test sandbox policy

`black_gravity_get_sandbox_policy` returns the normalized global policy and `sha256` for Windows LPAC tests. This policy caps `readRoots`, `writeRoots`, `network`, `childProcesses` and `maxOutputChars`. Initially it grants no external roots, disables networking, allows child processes and limits output to 4,000 characters.

For each Windows `black_gravity_test`, the MCP caller can choose `sandbox: { readPaths, writePaths, network, childProcesses, maxOutputChars }` within the ceiling. The bridge rejects paths outside approved roots and paths that overlap the original project, credentials, bridge storage, controlled temporary files, links, aliases or other protected paths. Test evidence records the selection and policy hash. The legacy `agy` executor retains its existing behavior and rejects an explicit selection.

To change the ceiling, read the policy and call `black_gravity_set_sandbox_policy` with its current hash and the proposal. `auto` applies validated proposals without a form. `ask` requires an interactive MCP form and checks the previous hash. Comparing the hash prevents overwriting a policy changed during evaluation. The caller selects verified, narrow grants per test within the policy. Delegated agents have no authority to choose, authorize or modify grants. Changes apply to new and queued tests. Active grants remain in force, and the bridge has no fallback to host execution.

Use specific verified directories, such as `"<approved-read-root>"` and `"<approved-write-root>"`, instead of entire disks or paths assumed to exist on another computer. In `ask`, confirm the ceiling in the form. In `auto`, submit the validated proposal. Select narrow subsets for the test.

## Temporary directory

Copies and their private baselines are created directly under the server's temporary directory (`os.tmpdir()`: `TMPDIR` on Linux and macOS, `TEMP` or `TMP` on Windows) with the `black-gravity-copy-` and `black-gravity-baseline-` prefixes. When that directory is a RAM `tmpfs` cleared at boot, retained copies are lost on restart and their tasks fail with `COPY_MISSING`. To keep copies across restarts, set `TMPDIR` in the MCP server entry's environment to a private directory on disk (owned by the server user, mode `0700`, a canonical absolute path without symbolic links, outside projects, the state directory and synced folders). Keep the value constant, because persisted copies must stay directly under the current temporary directory: if the server starts with a different temporary directory, tasks whose copy is not directly under the current temporary directory are quarantined (listed in `quarantinedTasks` of `black_gravity_health` and `black_gravity_tasks` with reason `copy-outside-temporary-directory`) while the server and other tasks keep working; restore the previous value to use them again, or discard them with `black_gravity_discard`, which only marks the record (discarded tasks stay listed in `black_gravity_tasks` with `discardedAt`) and never deletes the old copy (remove it by hand if no longer needed). Because `agy` looks for `.agents/`, `GEMINI.md` and `AGENTS.md` walking up from the copy, `TMPDIR` must be in a folder with none of these files above it.

### Secret exclusion and exception patterns

`BRIDGE_SECRET_EXCLUSIONS` is a JSON array of patterns relative to the project root. `BRIDGE_SECRET_EXCEPTIONS` uses a strict versioned object, for example `{"version": 2, "namePatterns": ["fixtures/.env.local"]}`. Both accept glob wildcards `*` (one segment), `?` (one character) and `**` (multiple directories). Traversal (`..`), NUL and absolute paths are rejected. Names without slashes match the basename in any directory, and `**/` and `/**/` match zero or more intervening directories. Matching is case-insensitive.

An invalid exception grants nothing. For exclusions, any error (invalid JSON, non-array, non-string, empty string, NUL, absolute path or `..`) disables the entire list. Task admission, baseline inspection, preflight and copy creation then fail with `INVALID_CONFIGURATION` before copying. Deny patterns are never silently dropped. The server stays up and health reports issues without configured values. Omission or `[]` normalizes to an empty list.

Use narrow exceptions for reviewed files without real credentials, such as the synthetic fixture in `BRIDGE_SECRET_EXCEPTIONS='{"version": 2, "namePatterns": ["fixtures/.env.local"]}'`. Precedence is:

1. Git ignores and unsafe path checks (`UNSAFE_PATH`) take priority over all exceptions.
2. An explicit exclusion (`BRIDGE_SECRET_EXCLUSIONS`, `SECRET_EXCLUSION`) takes priority over an exception.
3. A version-2 exception skips only the known filename check (`isKnownCredentialFile`, `SECRET_FILE`). All permitted content is still inspected by `detectSecretContent` and can be blocked with `SECRET_CONTENT`.

Preflight cannot guarantee detection of arbitrary secrets in source code, proprietary or unknown formats, encrypted data or obfuscated files.

### Safeguards for previews, context, and artifacts

Preview inspects known credential names and patterns before staging a copy of verified bytes in private Git and restores the private index with `read-tree HEAD`. Per-file reads (`readProjectPatch`) extract the slice directly from the reviewed and verified `preview.patch`, bound to its SHA-256. They avoid rereading the shared index or work tree. Generated or modified policy-violating files fail with `BLOCKED_FILE_DETECTED`. Changes during preparation invalidate the operation. Index restoration leaves existing Git objects in place.

Snapshots, fingerprints and forks apply origin and copy ignore rules and secret policy. Blocked generated files are omitted. A newly blocked baseline file causes `CONTEXT_CHANGED`. Supplied skills and execution policies retain their own integrity checks.

Artifact collection and reads reapply name, content and exclusion policies. Secret violations fail with `BLOCKED_ARTIFACT_PATH`. Reads verify bytes against the inspection and reference SHA-256 and keep only the requested window in memory. Earlier references still require path and policy checks. These checks cover recognized formats and cannot detect every secret or eliminate every filesystem race.

### CLI subprocess environment

`cliEnvironment` filters the CLI subprocess environment. The bridge logs no environment values and passes no tokens as arguments. Opt in to additional exact names with `BRIDGE_ALLOWED_ENV_VARS='["MY_TOOL_SETTING"]'`. Defaults allow no arbitrary injection or opt-in variables. Matching is case-insensitive on Windows and case-sensitive on Unix, Linux and macOS. Deduplication and `PATHEXT` are preserved.

Runtime injection and library preload names (`NODE_OPTIONS`, `NODE_PATH`, `LD_*` and `DYLD_*`) are forbidden in the allowlist and direct `cliEnvironment` calls, including case and whitespace variants on all platforms. The server ignores those and invalid names in `BRIDGE_ALLOWED_ENV_VARS` and reports `forbidden-name` or `invalid-name` without echoing values. Direct API calls throw. Legitimate non-injecting opt-ins, certificates such as `NODE_EXTRA_CA_CERTS`, system and profile settings, native keyrings, proxies, corporate certificates and official Google/ADC authentication are preserved. Other provider and third-party API credentials such as AWS, GitHub/GH, OpenAI and Stripe and local agents such as `SSH_AUTH_SOCK` and `GPG_AGENT_INFO` are omitted by default.

Default names grouped as in `cliEnvironment`:

- **System and executable resolution** — `PATH`, `PATHEXT`, `SystemRoot`, `SystemDrive`, `ComSpec`, `WINDIR`, `SHELL`, `TERM`, `COLORTERM`.
- **User and profile directories** — `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `HOMEDRIVE`, `HOMEPATH`, `USER`, `LOGNAME`, `USERNAME`.
- **Temporary directories** — `TEMP`, `TMP`, `TMPDIR`.
- **Locale, language and time zone** — `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `TZ`.

## OpenCode executor

`OpenCodeExecutionAdapter` (`src/opencode-execution-adapter.ts`, adapter version `'3'`) is registered alongside `agy` at server startup via `resolveOpenCodeRegistration` (`OPENCODE_PATH` or absolute `PATH` entries) and is reachable through MCP (`black_gravity_dispatch`, `black_gravity_handoff`, `black_gravity_health`, `black_gravity_capabilities`, `black_gravity_list_models`, `black_gravity_get_model`, and `black_gravity_set_model`; `black_gravity_run` and `black_gravity_compare` remain `agy`-only). It executes read-only and write tasks (`capabilities.write = 'supported'`, `capabilities.cancel = 'supported'`, `capabilities.resume = 'supported'`) via `opencode run --standalone --format json --archived --agent <agent>` (`black-gravity-read` in `read-only` mode, `black-gravity-write` in `write` mode) with the prompt passed over stdin and never passes `--auto`. `--standalone` starts an isolated private server per run instead of connecting to a shared background server so adapter environment variables take effect. Because OpenCode uses the bridge's fixed permission set, OpenCode tasks refuse `allowedTools` and `mcpServers` with `INVALID_AGENT_POLICY` and never inherit or enforce `agentPolicy`. `openCodeEnvironment` strips all inherited `OPENCODE_*` variables (case-insensitively on Windows) and sets `OPENCODE_DISABLE_PROJECT_CONFIG=1`, `OPENCODE_CONFIG_PROJECT_DISABLE=1`, `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, and `OPENCODE_CONFIG_CONTENT` with `formatter: false`, `lsp: false`, and the single primary agent and permission list for the selected mode (formatters are disabled in both modes because OpenCode executes them after edits without permission checks and they can evaluate repository configuration, verified for formatters; language servers are disabled as a precaution):

- **Read-only mode (`black-gravity-read`)** — `openCodeReadOnlyPermissions()` sets `* * deny`, `read * allow`, `glob * allow`, `grep * allow`, `external_directory * deny`, and `openCodeSecretReadRules()`.
- **Write mode (`black-gravity-write`)** — `openCodeWritePermissions()` sets `* * deny`, `read * allow`, `glob * allow`, `grep * allow`, `edit * allow`, `edit /* deny`, `edit ?:* deny`, `external_directory * deny`, and `openCodeSecretReadRules()`. Writes are performed only by file tools inside the isolated copy without an OS sandbox (`capabilities.sandbox = 'unsupported'`); shell commands and web tools are denied by OpenCode configuration, and tests run through the bridge test executor rather than the CLI. Because OpenCode exposes `opencode_worktree_remove` whenever `edit` is allowed and that tool checks `edit` (with an absolute path when outside the working directory) without checking `external_directory`, denying `edit` on `/*` and `?:*` after `edit * allow` blocks external `edit` and `opencode_worktree_remove` targets while keeping relative in-copy writes allowed.

In both modes, `openCodeSecretReadRules()` denies `read` on `*.env` and `*.env.*` and re-allows `*.env.example`, `*.env.sample`, `*.env.template`, and `*.env.dist`. Project `.env` files are not read by the OpenCode CLI, and instruction-only files such as `AGENTS.md` are skipped by the same project-config disable variables (though instruction-only skipping is not proven by an automated test). However, OpenCode's `grep` tool can still read `.env` files even when `read` denies them, so copy preflight remains the secret-exclusion control just as with `agy`. Neither main runs nor local test repairs convert line endings to LF for OpenCode (only `AgyExecutionAdapter` prepares and converts CRLF files), though the pre-launch refusal of non-UTF-8 text (`UNSUPPORTED_TEXT_ENCODING`) still applies to OpenCode write tasks. Preview and integration refuse patches touching OpenCode configuration (`opencode.json`, `opencode.jsonc`, `.opencode/`, and on Windows both `openco~N` and checksum 8.3 aliases matching `OP` plus four hexadecimal digits plus `~N`) with `AGENT_CONFIG_IN_PATCH`. Tool denials, failed tool calls, `background_wait` events, auto-rejected permission prompts, and any tool outside the mode's tool set (`['read', 'glob', 'grep']` in `read-only` mode; `['read', 'glob', 'grep', 'edit', 'write']` in `write` mode, so tools such as `opencode_worktree_remove`, `skill`, `shell`, or `apply_patch` are rejected) are reported as `EXECUTION_INCOMPLETE`, while process/protocol failures and spawn failures report `OPENCODE_PROCESS_FAILED` and `OPENCODE_UNAVAILABLE`.

The adapter requires an absolute `executable` path whose real path lies outside the task working directory (otherwise `OPENCODE_UNAVAILABLE`), sanitizes the child `PATH` via `sanitizeChildPath` to absolute, existing, deduplicated entries whose real path is outside the task working directory, and redacts values of at least eight characters from secret-named child environment variables (names matching TOKEN, SECRET, PASSWORD, PASSWD, API_KEY/APIKEY or CREDENTIAL) (including forms written with `\uXXXX`, `\"`, `\\` and `\/` JSON escapes) across responses, errors, stderr, and the bounded `raw` tool metadata.

**Cancellation, timeout, and process-tree reconciliation:** `opencode run --standalone` spawns a private `opencode` server child that calls `setsid`, placing it in its own session and process group outside `kill(-pgid)` of the run process. `OpenCodeAdapterOptions.containment` (`'auto'` by default, or `'none'`) and optional absolute `bwrapPath` control how the adapter contains and reaps these descendants:

- **Linux PID-namespace containment (`raw.containment = 'pid-namespace'`):** When `containment` is `'auto'` on Linux and bubblewrap is available (via `bwrapPath` or `detectBubblewrap()`), the adapter wraps both `opencode run` and the `session list` utility call with `bwrap --dev-bind / / --proc /proc --unshare-pid --die-with-parent --chdir <workingDirectory> -- <executable> ...` and reports per-launch containment `'contained'` through `onProcessLaunch` and `processCleanup.containment`. Right after spawn, the adapter captures the namespace link (`/proc/<child>/ns/pid`, accepted only when distinct from `/proc/self/ns/pid`) from a direct child of the outer `bwrap` process while the outer child is still unreaped (`exitCode === null && signalCode === null`). Stopping sends `SIGKILL` only to the outer `bwrap` handle (never signalling snapshot PIDs and without the `OPENCODE_TERMINATION_GRACE_MS` delay), so the kernel terminates every member of the namespace. Only a spontaneous exit of `bwrap` (exit code, no signal, no stop requested by the bridge) confirms cleanup as `verified: true` with `remaining: 0` regardless of initial namespace capture or `trackingFailed`; when the bridge kills `bwrap` (cancel, timeout, or adapter stop), when `bwrap` ends by a signal, or when `bwrap` has not closed, `countPidNamespaceMembers` polls `/proc/*/ns/pid` every 100 ms up to 3 s, and a failed capture leaves the cleanup unverified, marking the copy until it is discarded. **Limitation:** confirmation by spontaneous exit relies on `bwrap` reaping the namespace init before it exits (`bwrap` is trusted under the threat model).
- **Process-tree fallback (`raw.containment = 'process-tree'`):** On non-Linux platforms, when bubblewrap is unavailable, or when `containment` is `'none'`, the adapter declares baseline containment `'none'` (also reported per launch through `onProcessLaunch` and `processCleanup.containment`) and falls back to snapshot tracking. Right after spawn, it accepts the root `(pid, start)` identity only if `child` remains unreaped after the listing (otherwise marking tracking failed), polls descendants every 1,000 ms (capped at 256, marking tracking failed on overflow), and admits parent/child edges in `expandMatchedTargets` and `descendantIdentities` only when both `startOrder` values are finite and the child's `startOrder` is at least the parent's. On stop, `SIGTERM` is sent to the root process group (`-pid`) / `child` only while `child` is unreaped, and snapshot-derived descendants on Linux are signalled only after synchronously re-reading `/proc/<pid>/stat` to confirm their `starttime` still matches (`verifyProcessIdentity`). After `OPENCODE_TERMINATION_GRACE_MS` (3 s), the adapter sends `SIGKILL` to the root/group only while `child` is still unreaped, then runs `reconcileTrackedProcesses` (fixed-point descendant expansion without group kills, synchronously re-checking `/proc/<pid>/stat` `starttime` via `verifyIdentity` before each `SIGKILL`). This fallback path is best effort: snapshot polling can miss a detached process born and reparented between polls, and PID checks on Windows/macOS are not identity-bound; the `pid-namespace` containment path does not have these limits and is used automatically on Linux when bubblewrap is available.

Cleanup policy is decided by declared containment level (`contained`: kernel PID namespace proves every process ended; `tracked`: every process stays within reach of PID-plus-start-time reconciliation, as declared by `agy`; `none`: processes may escape tracking or record no identity, as declared by OpenCode outside the PID namespace). `TaskManager` immediately persists `processCleanup.verified = false` (alongside `containment` and, on Linux, `start`) in `onProcessStarted` before returning so a crash leaves an unverified launch marker on disk; `onProcessStarted` and `onProcessCleanup` are invoked inside `try/catch` (with the abort listener and stop path registered beforehand so if `onProcessStarted` throws, the adapter stops the run, waits for close, reconciles, and then rejects with the original error). `TaskManager` awaits reconciliation (with a 30-second post-abort safety bound that marks `processCleanup.verified = false`), restart recovery (`SERVER_RESTARTED` and `ORPHAN_PROCESS_RUNNING`) preserves the persisted marker, and `contained` and `none` launches with unconfirmed cleanup block automatic discard, retention eviction, and copy operations (`assertProcessesReconciled` and `assertCopyCleanupConfirmed`) with `PROCESS_CLEANUP_UNVERIFIED` until `black_gravity_discard` removes the copy. `tracked` launches (including Windows `agy` launches whose post-exit snapshot failed with no remaining processes observed; later identity confirmation via `reconcileLaunchIdentity` makes a single attempt only when it fits in the remaining task deadline and never extends the deadline, otherwise ending unconfirmed with its marker entry until the next on-demand reconciliation confirms it) are reconciled on demand by PID plus start time: tracked on-demand reconciliation signals only processes whose exact recorded start (Linux `/proc` start time) is re-checked right before the signal; on Windows and macOS no exact start is recorded, so it never signals and confirms only when the launch's processes (and their known descendants) are gone (Windows descendants whose intermediate parent already ended cannot be associated by parent PID and are outside that check); a process group whose leader is gone stays unconfirmed; and `tracked` launches do not block automatic discard or retention eviction. The Linux identity is recorded as `<boot_id>:<start ticks>` (or `boot-unavailable` when the boot ID cannot be read at recording time, which stays unconfirmed without any signal); a launch from a previous boot is confirmed without any signal, an identity without a boot ID or with an unreadable current boot ID stays unconfirmed without any signal, and records created before this change without `start` keep the previous rule. The resume-time `session list` check now runs under the same containment, process tracking, stop sequence, reconciliation, and `onProcessStarted`/`onProcessCleanup` reporting as `opencode run`, returning `processCleanup` on cancellation or timeout and recording its own per-copy unverified-cleanup marker entry when cleanup cannot be verified. The unconfirmed-cleanup guard (`assertCopyCleanupConfirmed`) runs inside the copy operation after the copy lock is taken and reads the marker from disk, so every operation on the copy (preview, patch reading, verification, recorded tests, integration, context, artifacts, and fork) passes it and sees a marker written by another bridge instance; `black_gravity_discard` is the only operation that skips it. Limitation: on the fallback path after a bridge process restart, previously spawned `setsid` server children are not tracked by the new bridge instance; persisted `running` tasks whose bridge owner and recorded PID have exited transition to `failed` (`SERVER_RESTARTED`).

**Provider errors, retry limit, and unknown effects:** Provider `error` and `retry` events are classified without including `response.body` and with precedence `host stop > provider code > EXECUTION_INCOMPLETE > OPENCODE_PROCESS_FAILED`: region refusal messages (`/hosted outside Europe and the United States|privacy#regions/i`) fail with `OPENCODE_REGION_UNAVAILABLE`, `provider.auth` fails with `OPENCODE_AUTH_REQUIRED`, and `provider.quota` fails with `OPENCODE_QUOTA_EXCEEDED`. Any classified `error` or `retry` event stops the run immediately; `retry` events are counted in `raw.providerRetries` regardless of a stored failure until the retry limit requests the stop, so the count stops at `MAX_OPENCODE_PROVIDER_RETRIES` + 1, and `MAX_OPENCODE_PROVIDER_RETRIES` (3) is enforced independently (`OPENCODE_RETRY_LIMIT`). When a run does not complete (`failed`, `cancelled`, or `timeout`), `raw.unknownEffects` records up to 10 redacted `{ tool, status }` entries for any `tool_use` call (`part.callID ?? part.id`) whose latest status is `pending` or `running`; because OpenCode 2.4.0's `--format json` output emits `tool_use` only once a tool finishes (`completed` or `error`) and never emits `pending` or `running` for in-flight tools, in `write` mode whenever a run does not complete and `step_start` events outnumber `step_finish` events (an interrupted step), the adapter also records a conservative `{ tool: 'unknown', status: 'interrupted' }` marker in `raw.unknownEffects` (deduplicated within the 10-entry bound). Whenever `raw.unknownEffects` is non-empty, `; effects unknown for: <tool>(<status>), …; inspect the copy before reuse` is appended to the error message, and the adapter never retries the run.

**Resume:** `TaskManager` refuses before spawning any process (`INVALID_SESSION`) when resuming an OpenCode task recorded by an earlier adapter version (such as version `'2'`). OpenCode resume requires the Bubblewrap PID namespace and is otherwise refused with `OPENCODE_RESUME_REQUIRES_PID_NAMESPACE` before launching any process (leaving no `process.started` event, `processCleanup`, or unverified-cleanup marker); only a spontaneous exit of `bwrap` (exit code, no signal, no stop requested by the bridge) confirms cleanup, whereas when the bridge kills `bwrap` (cancel, timeout, or adapter stop) the captured namespace is checked and a failed capture leaves the cleanup unverified, marking the copy until it is discarded. The adapter validates the session ID format (`/^ses_[A-Za-z0-9]{1,124}$/`, throwing `INVALID_SESSION`) and runs `opencode session list --standalone --format json` (under the `bwrap` PID-namespace wrapper) in the copy directory with the same mode environment before `opencode run`; the session is accepted only if an entry matches both `id` and the real path of `directory` against the task copy (missing, foreign, or unconfirmed sessions fail with `OPENCODE_SESSION_NOT_FOUND` without starting `opencode run`). When accepted, `--session <id>` is passed, any event reporting a different non-empty `sessionID` stops the run with `OPENCODE_SESSION_MISMATCH`, and `TaskManager` keeps `usageIsResume: false` (no `usageBaseline`) for both main and local test tasks when the executor is not `AgyExecutionAdapter` because OpenCode `step_finish` token counters are per run rather than cumulative across the session. **Limitation:** on macOS, Windows, Linux without usable Bubblewrap, or with `containment: 'none'`, OpenCode tasks cannot be resumed (start a new task); cancellation and timeout remain best effort, and confirmation by spontaneous exit relies on `bwrap` reaping the namespace init before it exits (`bwrap` is trusted under the threat model). The `linux-bwrap` CI job runs the OpenCode adapter and lifecycle tests alongside `linux-executor.test.js`.
